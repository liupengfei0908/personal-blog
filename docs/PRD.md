## 二、背景与目标

### 2.1 背景

个人没有对外展示的线上阵地，技能与项目经历只存在于简历与内部系统中，招聘方或潜在合作方无法在接触前快速了解作者能力。已确定采用方案 A（Astro 静态站点生成器 + 免费托管），MVP 骨架已开发完成并推送至 GitHub。

### 2.2 要解决的问题

1. 访客（招聘方/同行）无法在 1 分钟内了解「你是谁、会什么、做过什么」
2. 技术文章无沉淀处，学习与踩坑过程无法形成可回溯的记录
3. 维护成本必须趋近于零，否则个人项目必然烂尾

### 2.3 成功指标与口径

| 指标 | 目标值 | 口径 | 类型 |
|------|--------|------|------|
| 站点上线可访问 | 6 个页面全部 200 | 部署完成后逐页探测 HTTP 状态码 | 过程指标 |
| Lighthouse Performance | ≥ 90 分 | 首页移动端模式跑分 | 过程指标 |
| 核心内容可达性 | ≤ 2 次点击 | 从首页到任一作品详情/文章详情 | 过程指标 |
| 内容更新频率 | 月均 ≥ 1 篇 | 自然月内合并到 main 的文章数（目标值为估算） | 运营指标 |
| 月访问量（UV） | 上线 3 个月后 ≥ 100 | 去重访客数，以统计平台口径为准（目标值为估算） | 结果指标 |

## 三、名词与术语定义

| 术语 | 定义 |
|------|------|
| SSG | 静态站点生成器（Static Site Generator），构建期把内容与模板编译为纯 HTML |
| Astro | 本方案选用的 SSG 框架，原生支持 Markdown 页面 |
| frontmatter | Markdown 文件头部的 YAML 元数据（title/date/category），驱动列表页与文章页头部 |
| GitHub Pages | GitHub 免费静态托管服务，本方案的默认部署目标 |
| Lighthouse | Chrome 内置的站点质量跑分工具（性能/可访问性/SEO） |
| UV / PV | UV = 去重访客数；PV = 页面浏览总次数 |

## 四、需求范围

### 4.1 本期包含（MVP）

- 6 个页面：首页 / 关于我 / 作品集 / 博客列表 / 文章详情 / 联系方式
- Markdown 写作流：`src/pages/blog/*.md` 新建即自动进入列表（按日期倒序）
- 作品集数据化维护：`works.astro` 顶部数组驱动卡片渲染
- 响应式布局（桌面 + 移动端 360px 以上）
- GitHub 托管源码，push 即发布的部署流水线

### 4.2 本期不做（明确排除）

| 排除项 | 原因 | 归属 |
|--------|------|------|
| 评论互动 | 需引入第三方系统（Giscus 等），增加维护与合规成本 | 后续版本池 |
| 站内搜索 | 文章量少时列表页足够，量起来再评估 | 后续版本池 |
| 多语言 | 受众以中文招聘方为主 | 后续版本池（出海求职时触发） |
| 会员/登录 | 纯展示站，无此诉求 | 不做 |
| 自建统计后台 | 用第三方免费统计即可 | 不做 |
| 简历在线编辑 | 简历以脱敏 PDF 附件形式提供 | 不做 |

## 五、方案对比与选型说明

| 方案 | 实现成本 | 开发复杂度 | 用户体验 | 风险 | 上线时间 | 综合评价 |
|------|----------|------------|----------|------|----------|----------|
| A. Astro 静态生成 + GitHub/Vercel 托管 | 低（免费） | 低-中 | 好（纯静态、速度快） | 低 | 1-3 天 | **推荐（已实施）** |
| B. 建站平台（Notion/Framer/Wix） | 低（部分付费） | 极低 | 中（模板化） | 低 | 当天 | 否决：技术人设弱、不可定制 |
| C. 自建全栈 | 中-高 | 高 | 好 | 中（长期维护） | 1-2 周 | 否决：投入产出比低 |

**选型理由**：① 零成本托管；② 源码公开本身即技能背书；③ Markdown 写作 + Git 版本管理，维护成本最低。

**演进路径**：

| 阶段 | 内容 | 触发条件 |
|------|------|----------|
| 本期（M1-M3） | 骨架 → 内容替换+部署 → 统计接入 | 已排期 |
| 后续 v1.1 | 评论（Giscus）+ 站内搜索 | 文章数 ≥ 20 且月 UV ≥ 100 |
| 后续 v1.2 | 自定义域名 + SEO 强化（sitemap/OG） | 有稳定更新习惯后 |
| 后续 v2.0 | 英文版/多语言 | 目标转向海外机会时 |

## 六、用户角色与使用场景

| 角色 | 描述 | 核心目标 |
|------|------|----------|
| 站长（作者本人） | 前端工程师，内容唯一生产者 | 低成本发文、维护作品信息 |
| 访客-招聘方 | HR / 技术面试官，首次访问居多 | 1 分钟内判断候选人的技能与项目匹配度 |
| 访客-同行 | 开发者、潜在合作方 | 看文章与作品，找到联系方式 |

> 注：角色画像基于「求职导向为主、兼顾影响力」的已确认假设，非调研结论。

**场景 1（主流程）**：招聘方从简历链接进入首页 → 扫读一句话定位与技能标签 → 进入作品集看项目 → 下载简历或记录邮箱。

**场景 2（站长发文）**：本地新建 `.md` 文件 → 填 frontmatter → `git push` → CI 自动构建发布 → 线上可见。

**场景 3（异常）**：访客访问不存在的路径 → 看到 404 提示并可返回首页。

## 七、功能需求

| 编号 | 需求描述 | 业务规则 |
|------|----------|----------|
| FR-01 | 首页展示定位、技能、精选作品、最新文章 | 最新文章取博客列表前 2 篇；技能为标签形式，数量 ≤ 8 个 |
| FR-02 | 关于我页展示简介、经历、技能、简历入口 | 简历为脱敏 PDF，放 `public/` 目录；经历按时间倒序 |
| FR-03 | 作品集页以卡片展示项目 | 每个项目必须含四要素：背景/职责/成果/链接；只放可公开内容 |
| FR-04 | 博客列表页自动收录文章 | 数据源为 `src/pages/blog/*.md`，按 frontmatter 的 date 倒序；新增文件无需改代码 |
| FR-05 | 文章详情页渲染 Markdown | 页头展示 title/date/category；支持标题、列表、代码块样式 |
| FR-06 | 全局导航含当前页高亮 | 5 个导航项；当前页面对应项高亮 |
| FR-07 | 响应式布局 | 视口 ≥ 360px 无横向滚动；卡片栅格在窄屏降为单列 |
| FR-08 | 联系方式页仅展示公开渠道 | 邮箱 + GitHub；禁止出现手机号等敏感信息 |
| FR-09 | push 到 main 自动构建发布 | 构建失败时线上保持上一可用版本 |
| FR-10 | 占位内容可定位替换 | 所有示例文案处标注 TODO 注释，全局可搜索 |

### 验收标准（Given/When/Then）

**FR-04**
- Given `src/pages/blog/` 下有一篇 frontmatter 含 title/date/category 的 `hello.md`
- When 执行构建
- Then 博客列表页出现标题为「hello」的条目，且按 date 倒序排列；`/blog/hello/` 可访问返回 200

**FR-05**
- Given 一篇文章的 Markdown 含二级标题、有序列表与代码块
- When 访问该文章详情页
- Then 页头显示 title/date/category，正文标题、列表、代码块均按全局样式渲染

**FR-07**
- Given 视口宽度 375px 的移动设备
- When 访问首页与作品集页
- Then 无横向滚动条，作品卡片单列展示

**FR-09**
- Given 远端 main 分支当前线上版本正常
- When 推送一次会导致构建失败的提交
- Then 发布流水线标记失败，线上仍保持上一可用版本，且 GitHub 通知构建失败

## 九、业务流程与状态流转

### 9.1 内容发布流程

```
本地写作(.md) → git commit → git push → 托管平台构建 → 构建成功 → 线上更新
                                                  └→ 构建失败 → 线上保持旧版 + 失败通知
```

### 9.2 文章状态机

| 状态 | 含义 | 进入条件 | 允许操作 |
|------|------|----------|----------|
| 草稿 | 本地未提交 | 新建 .md 文件 | 编辑、删除 |
| 已提交 | 已 commit 未 push（或 push 到非 main 分支） | git commit | 修改（追加 commit）、推送 |
| 已发布 | 线上可访问 | push 到 main 且构建成功 | 修改（走新提交）、下线（删文件重新发布） |

规则：状态单向流转，不允许绕过 Git 直接改线上内容；下线文章 = 删除 .md 后重新发布。

## 十、数据与埋点需求

**本期最小数据能力（每版本至少 1 个核心看板）**：接入一个免费访问统计平台，提供 UV/PV 看板。

| 项 | 要求 |

## 十一、权限与安全要求

| 项 | 要求 |
|----|------|

| 内容合规 | 作品只放可公开内容；涉密项目仅做脱敏描述，不放源码与内部截图 |

## 十二、异常处理清单

| 编号 | 异常场景 | 处理方式 |
|------|----------|----------|
| EX-01 | 构建失败（语法错误/依赖问题） | 线上保持上一可用版本；流水线标红并通知站长 |
| EX-02 | 文章 frontmatter 缺 title/date/category | 构建期视为错误：本地 dev 即暴露，不允许带着缺失字段上线 |
| EX-03 | 访问不存在的路径 | 返回 404 页面，含返回首页链接 |
| EX-04 | 文章日期格式非法 | 列表排序按可解析日期处理；构建警告提示修正 |
| EX-05 | 文章中引用超大图片 | 写作约定：单图压缩后 ≤ 500KB；构建产物人工抽查 |
| EX-06 | 托管平台故障 | 静态产物 `dist/` 可一键切换备用平台（Vercel ↔ GitHub Pages） |
